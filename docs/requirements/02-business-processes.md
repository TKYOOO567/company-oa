记录日期：2026-10-23，Asia/Shanghai。状态：用于盘点、设计和验收准备的流程草案；具体旧规则未完成盘点，未实现、未执行业务验证。

## 1. 如何使用本文

**用户确认**：保留现用业务流程；各公司独立核算、部分客户/项目共享、总部汇总；需要完整会计核算；管理员可视化配置流程及表单。

**原系统观察**：只确认过固定审批列表共 60 条、付款申请字段页共 94 个字段等页面事实，尚未逐项还原全部旧流程。因此下述流程名称、角色称呼、状态名称和步骤衔接均为**设计建议或盘点模板**，不是用户已经批准的全部业务规则。

本文件不预设合同、开票、审批、收款、付款的强制顺序，不编造金额阈值、审批层级或处理时限。先记录原系统如何执行及员工实际如何处理，再确定配置和开发差异。引用的角色是责任类别，最终岗位和兼岗限制以确认结果为准。

## 2. 每条旧流程必须采集的内容〔盘点模板〕

| 维度 | 必须记录的证据与内容 |
| --- | --- |
| 身份及用途 | 原对象/审批标识、名称、启用状态、所属应用、业务目的、来源页面或导出样本 |
| 公司及关联 | 单据归属、人员身份、客户/项目/其他关联对象、跨公司协作与共享范围 |
| 字段及表单 | 字段标识、类型、必填/默认/校验规则、枚举、关联、附件、显示与可编辑条件 |
| 节点及路由 | 发起条件、节点、参与人计算方式、条件表达式、分支顺序及无匹配时行为 |
| 例外 | 原系统实际支持的退回、拒绝、撤回、转交、加签、代理、终止、更正及重复提交处理 |
| 业务副作用 | 何时更新台账或关联对象，何时通知、调用外部系统或生成后续单据 |
| 资金与会计 | 审批、实际收付、凭证及入账的对应关系；人工确认与自动动作的边界 |
| 版本与证据 | 发布/修改人及时间、在途实例兼容方式、历史日志及附件可提取方式 |
| 验收样例 | 正常、各条件边界、例外、越权样例及原系统结果；确认人、待核实项 |

不存在或无法提取的内容记录为“未发现”“不可提取”或“待核实”，说明检查范围；不能用猜测填入。对象数量、字段数量或列表截图不能代替这些规则。

## 3. 通用状态及责任模型〔设计建议〕

每笔业务分别关联三类事实：

1. **业务与审批事实**：提交内容、所用配置版本、节点处理人、处理结果及意见。
2. **资金事实**：实际收付、核验人、所属公司及相关证据。登记申请或审批完成本身不证明已经发生收付。
3. **会计事实**：凭证及其审核、记账、期间等状态。收付记录和审批结果不直接代替会计记录。

前端可将三类事实并列展示，服务端分别校验与保存。具体状态词、允许的转移和自动联动规则在盘点后确定。业务经办、审批处理、资金确认、会计处理、复核等责任如何分工，交由业务及财务确认，不因系统管理员能配置就默认其可代行全部业务操作。

## 4. FLOW-01 收入与收款

关联需求：REQ-001、REQ-002、REQ-004～REQ-006。拟议验收：AC-01、AC-04、AC-07、AC-08、AC-14、AC-15。

**目标**：追溯一笔收入相关业务、其实际收款与会计处理，同时保留原有业务流程。收款与收入的业务及核算口径需财务确认，不能仅凭到账状态自动决定科目或报表归属。

| 环节 | 需要落实的动作与证据 | 当前未知 |
| --- | --- | --- |
| 业务登记 | 记录原单据字段、公司归属及实际存在的客户/项目等关联 | 原对象与字段、是否必须关联其他单据 |
| 审批或审核 | 仅按旧规则中存在的审批/审核要求执行，保存处理轨迹 | 哪些收入或收款业务需要审批、其实际先后顺序 |
| 实际收款确认 | 由有权人员核对实际收款及其来源证据，关联业务和公司 | 确认方式、来源系统、分笔/合并收款是否存在及其规则 |
| 台账及差异 | 保留申请或业务金额与实际收款的可核对关系，标识未解决差异 | 差异、撤销、退款或更正的具体处理办法 |
| 会计衔接 | 根据已确认的核算规则关联后续会计处理，保留责任和状态 | 人工录入、生成草稿或其他自动化程度及触发条件 |

盘点时必须给出一笔真实完成业务的脱敏链路。对“审批已完成但未收款”“已收款但尚未入账”等情况分别展示实际状态，不能统一显示为全链路完成。退款、冲销等仅在确认旧业务或新要求后建立相应路径。

## 5. FLOW-02 支出与付款

关联需求：REQ-001、REQ-002、REQ-004～REQ-006。拟议验收：AC-01～AC-03、AC-05、AC-07、AC-14、AC-15。

**目标**：将付款申请、审批决定、实际付款和会计处理关联起来。原系统付款申请的 94 个字段只是盘点入口，不代表已确定字段含义或目标模型。

| 环节 | 需要落实的动作与证据 | 当前未知 |
| --- | --- | --- |
| 申请或登记 | 按实际字段登记公司、经办及相关业务资料，核对关联权限 | 单据类型、必填字段、合同/项目等关联要求 |
| 流程处理 | 复用核实后的节点、条件与人员规则，记录明确处理结果 | 金额或其他条件、退回/拒绝/转交等实际规则 |
| 付款核验 | 有权人员记录或确认实际付款事实并关联证据 | 审批与付款顺序、紧急或补单例外、实际付款来源 |
| 资金台账 | 关联申请与实际收付，识别未完成或待核对事项 | 是否有分次付款、合并付款及其分配方法 |
| 会计处理 | 使用经财务确认的流程形成会计记录及账务状态 | 凭证生成、审核、记账和更正规则 |

审批通过只改变相应审批事实，不直接标记实际付款或正式入账。系统不得因按钮重复点击、请求重试或配置更新而重复生成同一已确认动作；具体去重标识与重试策略由技术方案落实。这是拟议的工程约束，需通过实际实现验证。

## 6. FLOW-03 员工费用

关联需求：REQ-001、REQ-002、REQ-004～REQ-008。拟议验收：AC-02、AC-03、AC-06、AC-07、AC-10、AC-14。

**范围说明**：员工费用作为支出类业务的盘点场景。借款、报销、差旅、备用金等是否存在、是否需要分别建单，以原系统对象与实际业务为准，不将列举内容自动转为新增承诺。

建议按以下问题还原每种实际存在的费用单据：

1. 谁发起、归属哪个公司、费用发生人与经办人是否相同，需要哪些实际字段和附件？
2. 哪些内容由员工、负责人或财务补充，哪些节点可改、可看、可退回？
3. 审批后由谁确认实际支付，支付给谁；若发生借款抵扣、退回款或差额处理，原来如何执行？
4. 业务单据与资金记录、会计凭证如何关联，谁确认最终核对完成？

目标实现应以已核实的单据样例测试字段、节点及权限，分别显示申请、审批、支付和账务状态。跨公司任职、员工离职及代理处理须记录实际规则；不能仅依赖当前登录人员的默认部门推定每笔历史费用的核算归属。

## 7. FLOW-04 完整会计核算专项

关联需求：REQ-004～REQ-006。拟议验收：AC-14、AC-15。关键依赖：OPEN-001、OPEN-002、OPEN-008、OPEN-009。

**已确认现状**：原财务主要为收支台账，无完整会计分录。**已确认目标**：包含凭证、科目、结账、总账、正式会计报表。下列为设计工作顺序，不是已完成会计功能或会计政策建议。

| 工作环节 | 应形成的设计或业务决定 | 验证依据 |
| --- | --- | --- |
| 启用准备 | 每公司核算边界、启用账期、期初来源、历史补账范围、确认人 | 财务确认的启用及期初资料，不用推测数据补齐 |
| 规则及基础资料 | 科目及必要辅助信息、金额精度、期间规则、岗位责任 | 财务确认的规则与正反例；扩展专题另列范围 |
| 业务与凭证衔接 | 业务单据/资金记录与凭证的关联、触发方式、人工复核、异常处理 | 有来源、可追溯且状态独立的样例 |
| 凭证处理 | 录入或生成、校验、审核、记账、更正等动作和允许状态 | 财务确认的合法与应拒绝样例及预期结果 |
| 账簿与报表 | 总账与明细、各公司正式报表、总部所需汇总或正式报表 | 逐项数据来源、期间、公式、归属和核对样本 |
| 期间处理 | 结账前检查、结账、已结期间变更的受控处理与留痕 | 财务确认的期间控制及授权矩阵 |

正式账务修改必须有明确权限与可追溯规则；技术上如何保存历史、避免重复处理、处理失败或重试，由专项方案落实。不能把通用表单 CRUD 或查询图表直接认定为上述功能完成。

历史业务迁移可保留原始收支事实及来源标识，但历史分录、科目归属、期初或补账方案必须单独确认；导入成功本身不构成账务正确的证明。

## 8. FLOW-05 客户、项目共享与多公司核算

关联需求：REQ-004、REQ-007、REQ-008。拟议验收：AC-07、AC-08、AC-10、AC-15。

**设计建议**：记录每个共享对象的归属、共享对象/字段、可见范围、可修改范围及相关记录的独立权限。共享客户或项目不等于共享资金、会计资料；同一客户或项目的跨公司协作也不直接决定每笔单据的核算公司。

应从旧权限配置先形成矩阵，再由业务负责人核对实际协作例外。分别验证“允许共享的信息可访问”和“关联但未共享的信息仍受限”。总部汇总的范围、跨公司修改权及正式报表口径需明确，不从页面上的公司名称推定法律关系或报表规则。

## 9. FLOW-06 管理员可视化配置变更

关联需求：REQ-002、REQ-007、REQ-008。拟议验收：AC-09、AC-10。

**用户确认**：可配置字段、表单、审批节点、条件分支、权限。**设计建议**：采用以下可审查流程，具体审批责任及发布机制待设计评审。

1. 在现有有效版本基础上建立变更草稿，说明影响的业务、字段、节点、权限及数据。
2. 校验字段标识和关联、表单引用、路由及参与人；检查权限收紧/放宽、字段删除或类型变化对已有数据的影响。
3. 使用代表性样例预览，包括条件边界、无匹配分支、未授权人员和在途实例。
4. 由具备发布权限的人员发布新版本，保存变更人、时间、差异及验证证据；不以编辑页面保存成功替代发布验证。
5. 新实例按有效版本启动；建议在途实例保留原有效版本，历史记录保持可解释。若需迁移在途实例，另行制定映射、核对与恢复办法。
6. 发现问题时按可追溯方式停用或回退配置，不能静默覆盖历史定义；重新运行受影响用例。

发布后的版本规则属于工程建议，尚未完成业务确认或实现验证。旧字段删除、字段类型改变及权限调整的处理方式不能依赖浏览器本地存储实现。

## 10. FLOW-07 历史迁移与切换

关联需求：REQ-002、REQ-003、REQ-006、REQ-010。拟议验收：AC-11～AC-13、AC-18。

建议执行链路：**盘点实际导出 → 建立字段与关联映射 → 确定异常处理 → 试迁移 → 按对象和公司核对 → 演练在途切换 → 指定负责人验收**。尚未实际执行原系统导出或任何真实数据迁移。

- 保留来源记录标识、原始值、人员与公司对应关系及转换说明。无法可靠映射的记录进入异常清单，不默默丢弃或生成推测关联。
- 附件、评论、审批轨迹必须用实际导出样本确认可取得的范围；历史过程记录作为历史证据保存，不能伪装成新系统真实发生的审批操作。
- 在途单据是继续留在旧系统办结、迁入接续还是采用其他方式，由实际清单和业务决定确定；不在未确认时替用户选择。
- 数据总量、金额、状态、关键关联及附件/轨迹核对通过后，才形成迁移验收材料。业务数据迁移和历史会计账补建分开核对。
- 切换时间安排不依赖固定开发期限，但必须有负责人、准入标准、差异处置和恢复安排；这些见[开放问题](03-open-questions.md)。
