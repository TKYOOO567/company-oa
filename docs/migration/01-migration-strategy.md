# 历史数据迁移策略

文档状态：规划草案。更新日期：2026-10-23。当前阶段仅编写规则、文档和模板，尚未执行原系统导出、试导入或真实迁移，迁移工具也尚未实现。

本文服务于全面替换纷享销客的 Web 系统建设。历史业务、审批证据和公司归属需要保留；前端交互重新开发，Android 单独推进。各公司独立核算，指定客户或项目可以共享，总部可以汇总。业务范围以[需求基线](../requirements/01-scope-and-requirements.md)、[业务流程](../requirements/02-business-processes.md)及[待确认事项](../requirements/03-open-questions.md)为准，机器可读摘要见 [baseline.json](../requirements/baseline.json)。文档导航见 [docs/README.md](../README.md)。

追踪范围：REQ-002（保留流程）、REQ-003（历史迁移）、REQ-004（公司核算与共享）、REQ-005／REQ-006（完整会计目标与现有台账事实）；待决项沿用 OPEN-001、OPEN-004～OPEN-008。迁移验收对应 AC-11～AC-13，切换对应 AC-18；这些编号表示计划关联，不代表验收已执行。

## 1. 证据边界

| 项目 | 当前证据 | 仍须验证 |
| --- | --- | --- |
| 自定义对象 | 原系统管理页面显示 132 个 | 全量对象目录、各对象记录数、对象之间的依赖、停用或历史对象 |
| 固定审批 | 原系统管理页面显示 60 条 | 每条流程版本、节点、分支、权限和在途实例分布 |
| 付款申请字段 | 字段页面显示 94 个；已核对其中 14 个字段的标签、API 名称和类型 | 其余字段、必填约束、枚举实际值、关联目标、导出列名 |
| 导出入口 | 页面可见“全对象导出”和“按对象导出”入口 | 实际文件格式、导出完整性、限制、附件及审批轨迹是否随包提供 |
| 历史财务 | 用户说明目前以 Excel／手工收支台账为主，没有完整会计分录 | 账表样本、期初余额、账期、科目及是否需要历史补账 |

上述观察不等于已经取得导出文件，也不证明 132 个自定义对象都需要迁移。客户等标准对象不能混入“132 个自定义对象”的计数。当前 [object-inventory.json](object-inventory.json) 仅列少量已观察对象，并未列满全部对象。

[field-mapping.sample.json](field-mapping.sample.json) 是本项目的盘点与映射文档示例。它不是纷享销客真实导出 schema，也不是 O2OA 原生可直接导入的表单、流程或配置。英文目标键仅表示建议的逻辑字段；目标应用、表单、数据存储和适配接口仍需设计验证，不据此锁定数据库模型。付款日期 API 名按已读页面记录为 `field_PASr2__c`；后续必须与导出样本逐字核对，保留大小写。

## 2. 数据存放与证据保全

实际导出包、附件、含真实标识的 ID 映射、执行日志、备份及核对明细只存放在仓库忽略目录 `.local/migration/`，或公司控制、具备访问权限与备份的专用存储。目录组织约定如下；本轮不创建真实数据文件。

| 相对于工程根目录的路径 | 用途 |
| --- | --- |
| `.local/migration/<batch-id>/raw/` | 原始导出文件与原始附件包，验收封存后只读 |
| `.local/migration/<batch-id>/manifest/` | 文件清单、SHA-256 摘要、导出范围与批次说明 |
| `.local/migration/<batch-id>/samples/` | 脱敏后的关系样本；仍按内部数据保管 |
| `.local/migration/<batch-id>/staging/` | 可重建的解析与标准化中间数据 |
| `.local/migration/<batch-id>/id-map/` | 新旧 ID 对照及关联回填状态 |
| `.local/migration/<batch-id>/reports/` | 数量、金额、附件、权限与异常核对明细 |
| `.local/migration/<batch-id>/logs/` | 执行日志、逐项状态与重试记录 |
| `.local/migration/<batch-id>/backup/` | 试导入或切换前目标快照及回滚材料 |

`docs/` 只提交元数据、规则、空模板和人工合成示例。即使新仓库默认私有，也不提交真实客户、员工、联系方式、金额明细、银行信息、附件、令牌或真实新旧 ID 映射；公开 fork 及上游仓库同样不得出现这些数据。`.gitignore` 只是防误提交措施，不替代存储访问控制、加密和备份。摘要清单可能包含真实文件名，也应放在 `.local/`。

每次导出分配唯一批次号，登记导出操作者、源租户标识、公司与对象范围、筛选条件、导出开始及结束时间、源时区、页面或包内数量、文件大小和 SHA-256。对收到的文件先计算摘要，再将原件封存只读；解析、修复和脱敏只处理副本。再次取得的文件形成新批次，不覆盖旧包。

## 3. 从样本到全量的迁移步骤

1. **盘点并确定范围。** 补齐对象、字段、关联、用户组织、流程版本、附件和审批轨迹目录，区分仍使用、仅归档及不迁移项。按公司、对象、状态登记源记录数；对全对象导出入口先验证样本范围，不能把按钮名称当成完整性证明。
2. **取得并封存原始包。** 在允许的导出范围内取得文件，建立摘要清单，登记导出条件、遗漏和源修改时间。先只读检查格式、编码、分页或分包、列名、附件引用及源记录唯一 ID；不直接写入正式 O2OA。
3. **制作脱敏样本。** 从副本中用人工替换的公司、人员、客户、联系方式、金额和附件构造样本，保持引用关系、边界类型和分支覆盖。源 ID 也换成合成 ID。脱敏样本不得通过可逆字典或原附件内容泄露真实信息。
4. **核对字段和转换规则。** 逐一确认导出列与 API 字段的对应、必填约束、日期和时区、金额精度、币种、枚举、删除或停用状态及关联对象。`null`、空串和零值分别处理；不默默补零、不以显示名直接合并人员或客户。源只包含日期的字段保留日期语义，不擅自补成 UTC 时间。
5. **确定目标适配方案。** 将逻辑字段映射到经过验证的 O2OA 应用、表单、业务数据或归档结构。确认目标支持的写入方式、权限和审计行为后再实现适配器；禁止根据本目录 JSON 直接写目标数据库。旧流程配置需逐条重建和验证，不能假设与 O2OA 流程格式兼容。
6. **按依赖批次试导入。** 在隔离测试环境先建立公司、部门、人员映射，再处理客户／供应商、项目／合同／计划、业务申请、流水及归档材料。实际顺序以完整依赖图为准；循环关系采用先建记录、后回填关联。先小批量、再按公司或对象扩大，全部经过核对后才准备正式切换。
7. **恢复附件和审批证据。** 按第 5 节验证文件与权限，关联业务原记录；完整保存审批轨迹来源及上下文，明确历史归档与新系统运行实例的区别。
8. **执行核对与异常处理。** 为每个批次生成源／目标数量、金额、孤立引用、附件与流程状态报告。异常进入隔离清单，包含来源、原因、处理人和结果，修复后重跑相关批次；不得把失败行悄悄跳过并报告迁移完成。
9. **演练切换和回滚。** 使用生产等价的导出范围和已批准规则完成演练，验证冻结窗口、差异补迁、在途处理、目标备份及恢复。业务、财务和管理人员确认验收结果后安排切换；目前没有固定上线日期。

## 4. 新旧 ID、关系与幂等

保留来源系统、源租户、源对象 API 名和源记录 ID 组成的复合标识；不能把不同对象或公司中碰巧相同的 ID 当成同一记录。目标 ID 单独生成，并在迁移台账中保存对应关系、批次、源更新时间、源内容摘要、目标版本、执行结果及回填状态。来源缺少稳定 ID 时先列为阻塞项，另行确认可靠的唯一键，不能仅凭名称、行号或金额生成最终去重规则。

公司归属、核算主体和共享权限分别映射。共享客户仍保留其归属与授权范围；跨公司查看不改变财务归属。停用员工的历史姓名和源标识需要保留在受控档案中，不能自动把全部历史责任人改为当前管理员。

未来导入实现应以复合来源标识及迁移台账实现幂等：重复执行相同批次与内容应复用结果，不能重复创建申请、付款、流水、附件或凭证。源内容变化时按明确的版本与冲突策略处理；发生人工修改的目标记录不被无条件覆盖。关联回填、附件上传和重试均单独登记结果，支持失败后从检查点继续。

试导入与历史归档写入应避免触发真实付款、通知、审批待办、会计过账等业务副作用。是否允许触发及如何隔离须在目标适配验证中明确。导入一条“已付款”历史申请不意味着再次执行付款。

## 5. 附件与审批轨迹

导出入口是否提供附件实体、附件索引、审批意见、节点操作者、操作时间和历史流程版本尚待验证。先建立能力清单，再确定批量获取方式。

- 附件清单保留源业务 ID、源附件 ID、原始文件名、大小、媒体类型、摘要、获取结果、目标存储引用、业务归属及访问权限。签名 URL 或临时链接不能作为长期归档地址；授权获取后应将文件存入公司控制的目标存储，并记录来源。失败或缺失文件保留清单及原因，不伪装成迁移成功。
- 逐批校验附件数量、字节数和摘要；同一文件的物理去重不合并不同业务权限。前端下载及预览仍需检查所属业务和公司权限。附件上传重试使用稳定来源标识，避免重复挂载。
- 审批轨迹保留源单号、流程及版本、节点、操作者、结果、时间、意见、附件关系和可获取的代理／转交信息。无法导出的内容记录缺口，不能人工编造审批人、时间或“已审核”状态。
- 历史完成与退回流程优先作为可检索、可追溯的只读历史档案呈现，并标注来源。是否映射为 O2OA 已完成实例需专项验证；不得把旧审批记录伪造为新引擎真实执行的日志。在途实例另按第 6 节处理。

## 6. 在途业务和正式切换

在途流程必须单独盘点数量、当前节点、待处理人、金额、已执行动作及关联状态。不能仅导入表单后把它标记为“已迁移流程”。以下方案由业务负责人结合实际能力确认，目前未选定：

| 方案 | 必须具备的条件 |
| --- | --- |
| 旧系统办结，新申请走新系统 | 旧系统可继续受控使用；两侧受理界线、付款和数据汇总规则明确 |
| 撤回／终止旧实例后在新系统重新发起 | 业务确认可重办；保留旧证据与新旧单据链接；防止重复审批与重复付款 |
| 恢复到新引擎对应节点 | 技术与业务共同验证实例状态恢复、操作者及已执行动作；未验证前不承诺可无损恢复 |

正式切换前约定源系统停止受理或写入的时间点，并执行最后快照／增量补迁。只有证实源提供可靠更新时间、删除标记和增量范围后才采用增量；否则采用经验证的快照差异方案。补迁期间重新核对新增、修改、删除及付款状态变化。

确认新旧系统受理边界、流程待办去向、通知策略、财务记账边界、附件可访问性和应急入口后再开放新系统写入。需要保留多久的旧系统只读访问、账号及导出能力也应在停用前确定。

## 7. 核对与验收

核对基准必须来自同一导出范围及截止时间，不能以当前 UI 数量与更早快照直接比较。

| 维度 | 核对要求 |
| --- | --- |
| 数量 | 按公司、对象、状态、日期范围对比源记录、成功写入、去重、隔离和不迁移数；差额可解释且经确认 |
| 关系 | 所有应迁移关联可解析；孤立引用、循环关系回填和重复 ID 均有结果；历史停用用户可追溯 |
| 金额 | 按公司、币种、业务类型与状态分别核对合同、计划、申请、实收实付及台账汇总；使用确定的十进制精度，不用二进制浮点误差容忍掩盖差额 |
| 审批 | 完成、退回、撤回、在途数量及当前节点分别核对；来源轨迹完整性有清单；流程分支和权限经过业务验证 |
| 附件 | 清单、数量、字节、摘要、关联及下载权限通过核对；缺失项不被计为成功 |
| 幂等 | 相同输入重跑不增加业务记录或附件；失败重试不产生第二笔付款／流水／凭证 |
| 权限 | 各公司独立核算、指定共享客户／项目和总部汇总均有正反向验证；普通用户无法越权访问 |
| 恢复 | 目标备份可恢复；按批次撤回和切换失败后的续办路径演练通过 |

迁移台账要同时记录“已解析”“已写入”“已回填”“已核对”，不能以 HTTP 写入成功代替最终验收。原系统导出能力不足导致的缺口，应在验收报告中逐项说明并由负责人员决定处置。

## 8. 回滚与历史会计边界

试导入前保存目标快照，导入记录与批次绑定，保存目标修改前状态及副作用清单。失败时先停止新写入，再按批次台账撤销本批新增或恢复本批变更，不执行无范围删除。回滚操作须先在隔离环境演练，并重新核对附件、关联和权限。

切换后如已有新申请、人工修改、财务动作或真实银行付款，不能简单恢复旧快照覆盖全部数据。先封存新增数据与审计记录，核对外部实际动作，确定可逆范围；根据情况恢复旧系统受理、补录新业务或实施前向修复。数据库回滚不会撤销实际付款。

**业务台账迁移与会计补账是两个决定。** 当前历史资料以收支、银行／现金及往来台账为主，不能按字段映射自动声称生成了完整、合规的历史会计账。新系统要求完整会计核算，但启用日期、科目体系、期初余额、往来余额、会计期间、历史补建凭证范围及财务确认人仍待确认。不得从付款审批状态推断已经入账，也不得将流水金额直接当作会计期初余额。

在这些事项确认前，迁移规划只承诺保留可核对的源业务记录与关系；历史会计凭证生成、过账和结账规则单列需求及验收，不混在普通导入中执行。O2OA 目标会计能力及所需定制也需单独验证。

未来工具的输入、输出与失败处理契约见 [tools/migration/README.md](../../tools/migration/README.md)。
