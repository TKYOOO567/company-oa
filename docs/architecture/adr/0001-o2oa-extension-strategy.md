# ADR 0001：O2OA 扩展策略

- 状态：总体扩展策略继续有效；Web 第一版选型与实现进度由 [ADR 0002](0002-web-foundation.md) 和 [v0.1 记录](../../verification/web-v0.1.md) 补充，平台接入验收尚未完成。
- 工程身份：独立 `company-oa` 仓库，按上游源码快照建立新的 `main` 历史。
- 来源基线：用户 fork `TKYOOO567/OA` 的 `develop@0b328b1cd88e221d25a6188f47b3d6e08de69fbe`。该哈希不代表新工程初始提交；新提交以实际生成的 Git 记录为准。
- 适用范围：本公司 OA 的 Web 改造、平台扩展、业务配置及历史迁移。本期 Android、iOS 不改。
- 详细执行方案：[基于 O2OA fork 的改造方案](../02-o2oa-adaptation-plan.md)。

## 背景

用户要求全面替换纷享销客，保留现有业务流程并迁移历史数据，重新开发前端交互。员工先使用 Web，Android 后续单独推进。管理员需要可视化配置表单、流程和权限。

O2OA 已提供组织认证、流程表单设计及运行、查询和门户等通用能力。源码显示 Web 可以独立部署，设计态与运行态具备 REST 接口；同时，当前动态表单依赖 MooTools 与 MWF 运行时。重做员工界面可复用平台服务，但不能默认新前端直接兼容全部表单配置、脚本和权限行为。

本 ADR 固定职责边界和代码归属，避免将业务改造散落到平台源码。当前约定不意味着未运行的模块已经可构建，也不预先决定尚未验证的框架、数据库、SSO 和会计口径。

## 仓库来源与当前状态

新工程的源码来源与 Git 历史分别记录。根目录 [upstream.json](../../../upstream.json) 固定来源仓库、分支和提交：自有开发远端 `origin` 指向 `TKYOOO567/company-oa`，来源远端 `upstream` 指向用户 fork `TKYOOO567/OA`；实际绑定、提交和推送结果以 Git 记录为准，不宣称已包含完整上游历史。

导入源码的 [LICENSE](../../../LICENSE)、版权与上游说明保留。独立仓库及私有可见性不改变保留这些文件的约定。后续上游同步审查差异与兼容性，不覆盖公司改造。目录职责以 [仓库与目录规范](../01-repository-and-directories.md) 为准。

初始建档阶段仅有规划与来源基线；后续已进入 Web 第一版，新增员工界面和统一 API 适配器。后端业务扩展、公司应用配置、正式账务和真实迁移仍未完成。下文描述总体实施决定，实际检查结果以独立验证记录为准。

## 决定

1. **保留并复用 O2OA 平台能力。** 优先使用组织、认证、流程设计、表单设计、流程执行、动态表单、附件及查询能力。现有设计器暂复用，验证其支持管理员实际配置需求。

2. **员工业务 Web 独立维护于 `apps/oa-web/`。** 新建岗位导航、工作台、列表、详情与操作交互，通过统一 API 适配器访问平台及必要扩展。第一版选用 Vue 3、TypeScript、Vite，依据及验证边界见 [ADR 0002](0002-web-foundation.md)；动态表单运行时兼容仍需实测。

3. **动态表单以运行时兼容为先。** 先验证 MWF 表单的字段、校验、公式联动、脚本、附件、子表、读写权限和审批行为，再决定具体集成方式。独立页面、受控嵌入和重写渲染器均不是本 ADR 已确认的实现。

4. **公司业务配置与后端扩展分开管理。** 客户、项目、合同和资金业务以自定义应用及流程配置为基础；配置不能可靠承担的授权、约束、事务及专项逻辑使用必要扩展。扩展源码进入 `extensions/o2oa/`；实际模块注册、依赖、构建、接口注册及部署入口须验证并记录，不能假定新增目录自动接入平台。

5. **平台原目录保持可追踪。** `o2server/`、`o2web/`、`o2android/`、`o2ios/` 保留。确需修改上游源码时，采用最小变更，并在 `patches/o2oa/` 登记原因、基线、修改范围、验证结果及升级重放方式。不为实现方便而把公司业务散落在平台核心。

6. **导出配置作为业务版本资产。** 流程、表单、查询、门户及脱敏配置存入 `application-configs/`，记录依赖、来源和验证状态。真实数据、人员信息、附件、密钥和运行文件不混入配置版本。

7. **多公司授权由服务端执行。** 明确记录归属、核算主体、共享对象和总部范围；列表、详情、搜索、查询、统计、附件及导出使用一致授权边界。前端公司筛选及按钮显示不构成权限控制。

8. **会计核算作为独立专项推进。** 通用审批、流水和统计能力不能替代凭证、科目、总账、结账及会计报表。历史台账按来源字段迁移；正式建账时点、期初、历史补凭证及核算口径确认后再建立会计关联。

9. **迁移工具与部署模板各自归档。** `tools/migration/` 管理字段提取、映射、导入和核对；`deployment/` 管理公司云部署模板；`docs/` 管理全部项目文档；`.local/` 忽略真实导出、附件、数据库、日志和其他运行文件。

10. **先验证一条付款流程，再逐项完成全范围。** 付款纵向验证用于证明认证、API、动态表单、流程、权限、附件及扩展路径可用。它不是全部业务、完整会计或全量迁移的交付验收。

## 备选方向与取舍

| 方向 | 当前取舍 |
| --- | --- |
| 从零重做组织、认证、流程和全部设计器 | 暂不采用；先利用平台已有能力，避免在完整业务建模之前同时重建通用平台 |
| 直接修改原桌面，把所有公司业务放入 `o2web/` 和核心服务包 | 不作为常规方式；容易扩大升级冲突且职责不清，必要平台修改按补丁登记 |
| 只做新外壳，直接认定动态表单全部兼容 | 不成立；运行时及脚本、权限、附件需实测 |
| 一开始重写全部动态表单渲染器与设计器 | 暂不采用；先完成兼容验证，如不能满足需求，再根据证据提出替代 ADR |
| 先实现并同时交付 Web 与 Android | 本期不采用；用户已要求两条线分开，先做 Web |

## 后果

可复用的通用能力减少重建范围，员工使用界面可以围绕岗位重新设计。业务配置版本、后端扩展和平台补丁分开保存，后续升级有明确核对入口。

需要持续维护新 Web 与 O2OA 的 API 契约；动态表单运行时会形成兼容边界。现有设计器与新业务 Web 可能存在界面差异，管理员任务完成能力和配置生效行为须验证。公司业务模型、服务端授权、会计专项和历史迁移仍需实质开发，不能因采用 O2OA 而视为自动具备。

## 验证和后续决策

采用本约定后的第一轮技术验证必须证明：

- 平台在隔离环境中的真实构建、启动及 Web 独立访问方式。
- 登录、当前用户、会话到期、登出和统一 API 适配路径。
- 配置导出导入及动态表单、审批、附件的完整执行。
- 后端扩展实际注册、构建及部署的接入方式。
- 多公司允许和拒绝场景，包含直接访问接口、附件与导出。
- 一条按现有规则配置的付款流程及其异常、回退和版本行为。

框架与构建工具、数据库、认证部署与 SSO、动态表单集成方式、会计建账与核算口径均保留待决。按 [改造方案](../02-o2oa-adaptation-plan.md#5-分阶段推进与验收门槛) 的阶段入口和退出标准推进，完整业务与迁移另行验收。

用户要求优先于本文。常规实现及已授权范围内的验证修复不要求额外审批；出现业务信息缺失或真实目标冲突时补充澄清。后续证据改变本策略时，用新的 ADR 记录替代关系和依据。
