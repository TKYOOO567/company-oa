# 仓库与目录规范

状态：用户已同意的规划在本工程中的目录约定。先读 [开发约束](../../AGENTS.md) 与 [需求范围](../requirements/01-scope-and-requirements.md)。

## 1. 仓库身份

本工程为独立开发仓库，保留导入的 O2OA 源码基线；`origin` 指向新的 Company OA 开发仓库，`upstream` 指向用户提供的 `TKYOOO567/OA` fork。来源分支、提交和原项目地址见 [upstream.json](../../upstream.json)。

新的 `main` 历史从源码快照开始，来源提交属于上游仓库，不应误认为本工程已有同一提交历史。许可证、版权及上游说明保留。同步上游时先审查差异，验证兼容后再合入；不得用覆盖目录的方式抹掉业务变更。

本地工作区只保留 `company-oa/` 一个项目目录及工作区入口说明。所需 fork 源码已经纳入本仓库，开发、构建和运行不得依赖兄弟目录中的源码、独立原型、符号链接或本地路径包；`upstream` 只作为远程来源追踪。后续复用代码、设计资料和工具直接放入本仓库对应目录。

## 2. 顶层布局

```text
company-oa/
├── AGENTS.md
├── docs/                        需求、架构、迁移、验证文档
├── apps/oa-web/                  新 Web 业务前端
├── extensions/o2oa/              后端适配和业务扩展
├── application-configs/          脱敏设计配置与版本
├── tools/migration/              迁移工具源码
├── deployment/                   公司云部署模板与运维说明
├── patches/o2oa/                 上游修改登记
├── .local/                      忽略的真实数据、日志与临时文件
├── upstream.json                上游来源与固定提交
├── o2server/                    上游服务端
├── o2web/                       上游平台 Web 与设计器
├── o2android/                   Android 迁移说明，本期不开发
└── o2ios/                       iOS 迁移说明，本期不开发
```

当前新增工程目录只放职责说明，不创建空壳业务程序。源码语言、前端框架和部署拓扑等在技术验证后确定。

## 3. 变更放置规则

| 变更 | 首选位置 | 说明 |
| --- | --- | --- |
| 岗位导航、工作台、列表、详情、员工表单交互 | `apps/oa-web/` | 独立维护包管理、构建与组件；统一适配认证与 API |
| 公司授权、业务校验、事务和必要平台接口适配 | `extensions/o2oa/` | 先验证 Maven 模块、接口注册与运行装配，再记准确入口 |
| 流程、表单、门户、查询、统计设计定义 | `application-configs/` | 保存可追踪的脱敏导出版本，不混入业务记录 |
| 原系统解析、字段转换、导入和核对 | `tools/migration/` | 工具与原始数据分离，支持批次、幂等和错误回溯 |
| 反向代理、环境变量样例、备份恢复和部署说明 | `deployment/` | 只提交模板，密钥与实际配置由运行环境管理 |
| 必要的 O2OA 核心修改 | 原准确源码位置＋`patches/o2oa/` 登记 | 保留原因、影响、验证与上游升级处理方式 |
| 真实导出、附件、银行资料、凭证、数据库、日志 | `.local/` 或部署环境专用存储 | 不进入 Git；是否脱敏与保留期限按实际使用确认 |

## 4. 建议的后续内部结构

以下是代码阶段的建议，不表示当前已建立或已选定框架。

- `apps/oa-web/`：界面、业务功能、公共组件、API 适配、认证与授权状态展示分别维护；页面不自行拼接平台认证协议。
- `extensions/o2oa/`：按业务能力拆分适配、授权和服务；不预设每个目录都是独立进程或微服务。
- `application-configs/<application>/<version>/`：设计定义、依赖清单、来源及验证记录；平台原生导出格式以实测为准。
- `tools/migration/`：源格式解析、映射、目标导入、验证分别实现；运行输入和输出在 `.local/migration/<batch>/`。
- `deployment/`：开发、验证和生产的模板分开，不能把验证环境默认配置直接当生产配置。

## 5. 命名与版本

- 自有目录和文件优先使用稳定英文小写及连字符，正文使用中文。上游文件保持原命名。
- 需求保留 `REQ-001` 等稳定编号；开放事项、技术决定和验收用例分别编号并互相引用。
- 字段的显示名称、源 API 名、建议逻辑目标和最终存储字段分开记录；文档样例不锁定数据库结构。
- 接口、配置或共享范围变化时同步更新文档和验收用例。流程配置变更对在途实例的影响要有实测记录。
- 新 Web 选定包管理器后提交对应锁文件；根上游忽略规则不应导致自有工程的锁文件丢失。
- 初始化中间文件和已被正式文档替代的草稿及时清理；不为旧原型或重复源码另建长期副本。

## 6. Git 与来源追踪

- `main` 保存可追踪的阶段成果，功能开发按任务建立短期分支；不要求为本轮文档编造业务实现。
- `origin` 是自有开发仓库；`upstream` 是用户提供的 fork。初次导入不宣称已包含完整上游 Git 历史。
- 上游源码快照、目录与需求文档分别提交，方便核对本轮是否触碰业务实现。
- 本工程按用户要求公开，并保留原 fork 的许可证及版权说明；真实数据、密钥和运行文件排除在版本管理之外。
- 后续权限测试和迁移核对都使用可回溯证据，不能仅凭界面截图或成功提示认定完整通过。

详细改造步骤见 [改造方案](02-o2oa-adaptation-plan.md)，迁移边界见 [迁移策略](../migration/01-migration-strategy.md)。
