# 基于 O2OA fork 的改造方案

本文状态：当前改造方案已建档，业务实现与技术验收尚未开始。已确认事项是后续工作的约束；标为待验证、待确认的事项不视为已经选型或已经实现。

本工程为独立的 `company-oa` 开发仓库，按固定上游源码快照建立新的 `main` 历史。源码来自用户 fork `TKYOOO567/OA` 的 `develop@0b328b1cd88e221d25a6188f47b3d6e08de69fbe`；该哈希是来源仓库的提交，不是新工程初始提交。新 `main` 的初始提交以实际生成的 Git 记录为准，不宣称继承了完整上游历史。

来源、固定提交及远端规划见根目录 [upstream.json](../../upstream.json)：`origin` 为自有开发仓库 `TKYOOO567/company-oa`，`upstream` 为来源 fork `TKYOOO567/OA`；实际绑定与推送状态以 Git 记录为准。保留导入的 [LICENSE](../../LICENSE)、上游版权及相关说明，不因建立独立仓库而删除或替换。目录规则见 [仓库与目录规范](01-repository-and-directories.md)。

## 1. 目标与边界

新系统全面替换纷享销客，保留经核对的现有业务流程，迁移历史数据，重新开发员工使用的 Web 导航、工作台、列表、详情与操作交互。本期只推进 Web；Android 独立安排，移动端目录当前仅保留迁移说明，本期不改；实际客户端源码位于上游另行维护的仓库。

需求基线包括审批、客户管理、财务报表、公司流水、历史迁移及完整会计核算；项目、合同、收付款等关联业务按原系统实际流程纳入盘点和改造，具体类型及规则仍需核对。完整会计核算包括凭证、科目、总账、结账与正式会计报表；它的工作量和验收不能被“已有审批及报表设计器”替代。稳定需求编号及确认等级见 [需求范围](../requirements/01-scope-and-requirements.md)。

各公司独立核算，部分客户和项目可共享，总部可汇总。目标部署在公司控制的云服务器，允许员工通过互联网登录；当前尚未部署。上线不设固定日期，以完整业务验证、迁移核对和切换准备通过为准。

管理员需通过可视化界面调整表单字段、审批节点、条件分支及权限。新员工 Web 与现有设计器可以采用不同界面；保留设计器时，仍需验证管理员能够完成这些实际配置任务。

用户明确要求优先于本文。已经授权范围内的常规实现、验证和修复直接推进；只有缺失的业务口径、权限边界或会影响已确认目标的变更需要补充澄清，不将日常实现逐项变成审批事项。

## 4. 改造结构与复用边界

```text
员工浏览器
  └─ apps/oa-web：岗位工作台与业务交互
       └─ 统一 API 适配器
            ├─ O2OA 组织、认证、流程与表单运行接口
            ├─ O2OA 自定义应用、查询、统计、附件接口
            └─ 必要业务扩展：公司授权、业务约束、事务与专项服务

管理员浏览器
  └─ 现有 O2OA 设计器及管理入口
       └─ 流程、表单、查询、门户与权限配置
            └─ application-configs 中维护脱敏导出版本

历史导出文件 → tools/migration → 校验、映射、试导入、核对 → 新系统
```

此结构表达职责关系，尚未决定前端框架、具体接口代理位置、扩展模块装配方式、数据库和部署拓扑。

### 4.1 统一 API 适配器

员工页面通过统一适配器访问平台服务，不在每个页面各自拼接 O2OA 地址、认证头和错误处理。适配器承担：

- 服务地址发现或代理配置、请求封装、分页与业务状态映射。
- 登录、登出、当前用户、会话到期和接口错误的统一处理。
- 业务标识与平台应用、流程、工作、任务、组织标识之间的明确映射。
- 可见公司范围、可用操作与表单权限的读取；提交时携带明确的业务上下文。
- 接口契约和错误语义的固定，避免平台升级影响所有业务页面。

适配器不是服务端授权替代品，也不默认具有管理员权限。认证 token 的格式、刷新机制、存储方式、同源部署与跨域访问由技术验证决定，不依据名称推定为 JWT 或 Bearer。

### 4.2 动态表单与设计器

优先验证保留 MWF 表单运行时、复用现有设计器的方案。新 Web 可先重做外围交互，再通过经验证的接口展示动态表单。具体采用独立路由、受控嵌入或其他兼容方式，由验证结果决定，不提前宣布已能无缝集成。

技术验证至少覆盖字段校验、公式和联动、组织选择、子表、附件、字段读写控制、审批动作、退回和再次提交。包含脚本的表单需列出运行依赖，验证新页面的生命周期、数据保存和脚本上下文。

若采用嵌入方式，验证登录态、页面导航、消息来源校验、尺寸与弹窗、附件下载、错误回传及退出；若重写渲染器，须明确支持的配置格式和组件范围，并证明已有配置可用。两种方式均不得以隐藏按钮代替服务端权限。

管理员的表单与流程配置入口暂复用 O2OA。管理员修改后，新 Web 必须能按约定生效；发布、版本、已有实例与新实例的行为需形成测试记录。

### 4.3 公司业务应用与必要扩展

客户、项目、合同、付款、回款及台账以 O2OA 自定义应用、表单、流程、查询为基础进行建模。能可靠配置的规则进入配置版本；平台配置不能保证的授权、跨记录约束、业务事务、唯一性与核对逻辑进入必要扩展。

扩展实现前须验证真实模块入口、Java 依赖、构建注册、接口注册与部署方式，并补充接入说明。不得直接在原平台包中散落公司业务，也不得声称 `extensions/o2oa/` 下的源码已经自动参与构建。

### 4.4 多公司与共享授权

每条公司业务记录必须具有明确的归属及核算主体。共享客户、共享项目需要明确共享对象、共享公司、可用操作和授权来源；总部汇总范围与普通员工权限分别定义。

所有列表、详情、查询、统计、搜索、附件、导出和关联选择接口必须在服务端应用一致的授权边界。修改公司参数、直接请求记录 ID 或绕过前端调用接口，不应扩大数据范围。不同公司用户的允许与拒绝场景都必须验证。

前端公司切换只表达用户当前查看范围。它不授予权限、不改变记录归属，也不等同于独立账套。正式会计的账套、核算主体和总部汇总规则须在财务专项中确认。

### 4.5 会计核算专项

现有 Excel／手工记录主要是收支台账，没有完整会计分录。原系统字段映射能够帮助迁移记录，不能自动补齐凭证、科目、期初、期间和结账关系。

会计专项单独定义账套与科目、期初余额、凭证及审核、期间与结账、往来核销、总账与明细账、报表口径，以及原始业务与会计记录的追溯关系。审批通过、银行实际付款、流水确认、生成凭证和凭证记账是不同业务事件，其具体触发及撤销规则需要逐项确认。

正式建账时点、历史是否补建凭证、余额如何取得及核对、采用何种会计口径目前待定。未确认前不得将历史收支台账直接标为已记账凭证，不得将通用统计页面称为完整会计报表。

### 4.6 历史迁移

按原纷享销客实际导出字段建立映射，先取得小范围脱敏样本，再确定每类对象的导入途径。对象迁移需覆盖归属公司、人员和组织映射、客户与项目及合同关联、金额与状态、流程记录、附件和时间字段；具体可导出性以样本及实际导出结果为准。

每批迁移保存源记录标识、目标标识、映射版本、执行批次和失败原因。重复执行不得产生无法识别的重复记录。关联对象按依赖顺序处理；不确定的关联、缺失人员、重复客户及无效字段进入异常清单。

核对包括对象数量、关联完整性、金额合计、往来余额、附件数量及可读性、抽样业务追溯和公司权限。无法导出的审批日志、附件或原状态须单独登记保留方式与影响，不能默认为迁移成功。

### 5.1 付款流程验证的最小证据

选定的真实付款流程需先核对申请字段、公司及项目合同关联、审批条件、审批人、金额规则和财务处理方式。尚未核对的会签、加签、撤回、退回、转交或金额触发条件不能凭通用节点能力推定存在。

验证记录至少包含：

1. 普通员工提交并保存正确数据、附件与业务关联。
2. 条件分支及审批人按已确认配置计算，待办、详情和审批历史一致。
3. 管理员修改字段或规则并发布后，新旧实例按已定义的版本行为执行。
4. 无权限用户直接调用接口时被拒绝；跨公司共享及总部汇总按授权工作。
5. 对重复提交、接口失败、附件失败及已处理任务再次操作给出明确结果。
6. 审批完成与实际付款、流水、记账之间按已确认边界关联，未实现环节明确列为缺口。

这条流程的作用是验证整体改造路径。其通过不代表全部审批、财务、CRM、历史迁移已经完成。
